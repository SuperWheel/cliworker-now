## Context

仓库已具有 TypeScript ESM、React、Cordis/Gateway 分层和完整测试、隔离构建入口。`doc/design.md` 从单 Antigravity MVP 演进到多 CLI，`doc/tasks.md` 保存跨版本记录；两者不能全文等同于当前规格。当前工作区另有用户的 Logo 归档和文档整理，需完整保留。

## Goals / Non-Goals

**Goals:**
- 开发者通过仓库锁文件获得同一 OpenSpec 版本，并可在 Codex 或终端管理变更。
- 后续变更有清晰的需求、设计、任务和实际验证入口。
- 保留历史证据、用户已有授权及插件运行边界。

**Non-Goals:**
- 不接入新的运行时能力，不把 OpenSpec 集成为插件界面功能。
- 不为所有业务域补写规格，不宣称重新验证了所有 CLI。
- 不安装全局技能或修改全局 OpenSpec 配置，不引入外部 store、云端同步或 CI 平台。

## Decisions

1. **固定开发依赖，使用 `pnpm spec`。** 相比全局安装或每次 dlx latest，项目锁文件可复现；脚本局部设置 `OPENSPEC_TELEMETRY=0`，不写机器全局偏好。官方生成技能保留原文，`AGENTS.md` 和配置指导将裸 `openspec` 命令替换为项目入口。
2. **官方 schema + 项目 context/rules。** 使用 `spec-driven`，不维护自定义 schema；新增/修改规则写入配置，便于以后升级生成技能。Codex core 的六项技能足够完成当前闭环。
3. **先建立开发流程规格，业务域按需增加。** `doc/openspec.md` 给出源码和测试索引；已有命名角色能力不会因旧计划记忆而再列待实现。
4. **规格、设计史和验收证据各有位置。** 新 change 存本次任务；归档合并已落实的规格。设计史只追加最新决策和入口；实际验证继续追加到 `doc/tasks.md`，不批量勾选旧版本待办。
5. **验证范围与影响匹配。** 严格校验、配置注入、归档检查及冻结锁文件验证覆盖工具接入；类型检查、现有测试和隔离构建检查依赖变化。无运行时改动，正式 build、Desktop 更新和真实模型调用不属于本次验收。

## Risks / Trade-offs

- [规格覆盖不完整] → 明确业务域尚未建立当前规格，不将缺失解读为功能不存在；实际变更时对照源码和测试补齐。
- [生成技能使用裸 CLI] → 本地 `pnpm spec` 是统一入口；不手改生成模板，避免升级时丢失定制。
- [格式校验被误当成功] → 每项任务保留实际结果与边界；未完成的所需验收不能通过归档隐藏。
- [上游文档比安装版本更新] → 以锁定版本的 `--help` 和 `instructions` 为准；升级单独处理。
- [混入其他工作区改动] → 只暂存本次新增文件和文档增量，保留用户原有资产整理及历史文档差异。

## Migration Plan

本次仅新增工作流，无运行数据迁移。先生成项目文件、说明和任务，核验后归档本次 change。回退时移除本次开发依赖、脚本和新增 OpenSpec 文件，并恢复本次文档增量；不得回退用户原有未提交修改。后续新增其他开发助手可显式运行 `pnpm spec init --tools <tool-id>`，不把插件支持的全部 CLI 自动当作开发工具安装。

## Open Questions

无阻塞问题。其他开发助手的专用入口以及首个业务功能 change，在用户有实际需求时选择。
